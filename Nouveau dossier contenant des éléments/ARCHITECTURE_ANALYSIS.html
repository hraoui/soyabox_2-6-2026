Fonctionnement offline-first

L'application fonctionne entièrement en mode local avec Isar :

  • Toutes les opérations CRUD passent d'abord par Isar local
  • La synchronisation est asynchrone et se fait en arrière-plan
  • Les commandes sont créées localement puis poussées vers l'API
  • Les produits/catégories sont importés depuis l'API puis stockés localement
  • L'authentification fonctionne en online-first avec fallback local

5. Système de Synchronisation

Architecture multi-couche

┌─────────────────────────────────────────────────────────┐
│                    Sync Controller                       │
│  (Déclenche la sync, gère le background sync)           │
└──────────────────────┬──────────────────────────────────┘
                       │
        ┌──────────────┴──────────────┐
        │                             │
┌───────▼────────┐          ┌────────▼────────┐
│  Sync Queue    │          │  Order Pull     │
│  Service       │          │  Service        │
│  (Push local   │          │  (Pull API      │
│   → API)       │          │   → Local)      │
└───────┬────────┘          └────────┬────────┘
        │                             │
        │  • File d'attente JSON      │  • Récupère commandes API
        │  • Retry exponentiel        │  • Stocke localement
        │  • Dead letter queue        │  • Marque comme sync
        │  • Deduplication            │  • Notification sonore
        │  • Lock (synchronized)      │
        │                             │
┌───────▼─────────────────────────────▼────────┐
│           Order Daily Sync Repo              │
│  (Orchestre sync quotidienne par batch)      │
└───────────────────────┬──────────────────────┘
                        │
              ┌─────────┴──────────┐
              │                    │
        ┌─────▼─────┐      ┌──────▼──────┐
        │  Isar DB  │      │  API REST   │
        │  (Local)  │      │  (Remote)   │
        └───────────┘      └─────────────┘

Caractéristiques de SyncQueueService

  • File persistée en JSON sur le disque
  • Déduplication par dedupeKey par type d'entité
  • Flush périodique toutes les 45 secondes
  • Rate limit handling avec backoff exponentiel
  • Dead letter queue pour les items échoués
  • Per-entity sync state (orders_sync_state.json, etc.)
  • Prévention des race conditions via synchronized Lock

9. Injection de Dépendances

// dependencies.dart
class DependencyInjection {
  static Future<void> init() async {
    // 1. Services initialisés en premier
    await AuthSessionService.instance.init();
    await AppSettingsService.instance.init();

    // 2. API Client (permanent pour garder le token)
    Get.put(ApiClient(...), permanent: true);

    // 3. Repositories
    Get.put(CategoryRepo(apiClient: Get.find()));
    Get.put(ProductRepo(apiClient: Get.find()));

    // 4. Controllers permanents
    Get.put<AuthController>(AuthController(), permanent: true);
    Get.put<PosController>(PosController(), permanent: true);
    Get.put<SyncController>(SyncController(), permanent: true);

    // 5. Controllers lazy
    Get.lazyPut<ImportController>(() => ImportController());

    // 6. Sync services
    await SyncQueueService.instance.init(...);
    await ApiOrderPullService.instance.init(...);

    // 7. Repo factory avec injection
    Get.lazyPut<OrderDailySyncRepository>(
      () => OrderDailySyncRepository.create(
        baseUrl: AppConstant.baseUrl,
        authToken: startupToken,
        localDb: Get.find<IsarOrderLocalDatabase>(),
      ),
    );
  }
}

10. Problème PIN Code - Diagnostic & Solution

⚠️ Problème identifié

Le PIN code 2026soya pour Super Admin et soya2026 pour Admin ne fonctionnent pas car :

  1. Le UserSeeder ne s'exécute qu'une seule fois (fichier flag .user_seeder_has_run_v2)
  2. Sur ton installation existante, les utilisateurs ont été créés sans PIN (pinCode: null)
  3. Le seeder détecte le flag et saute le seeding, donc les PINs ne sont pas ajoutés

✅ Solution - Réinitialiser la base de données

Pour une nouvelle installation avec les PINs correctement configurés :

# Supprimer la base Isar existante et le flag du seeder
rm -rf ~/Library/Application\ Support/com.soyabox.caisse1/
rm -rf ~/Library/Application\ Support/.user_seeder_has_run_v2

# Ou via Finder (macOS) :
# Aller à ~/Library/Application Support/ et supprimer le dossier de l'app

Ensuite, relancer l'application - le seeder recréera les utilisateurs avec les PINs.

Fonctionnement offline-first

L'application est conçue pour fonctionner 100% en local sans toucher au code :

  • ✅ Authentification : Login avec PIN (superadmin/admin) ou email+password (staff)
  • ✅ POS : Création de commandes, paiements, gestion des tables
  • ✅ Admin : Dashboard, comptabilité, gestion utilisateurs
