1. Vue d'Ensemble

SOYABOX POS est une application de point de vente (caisse) conçue pour la gestion de restaurants avec support multi-serveurs, multi-tables, et synchronisation bidirectionnelle avec un backend Laravel.

🎯 Fonctionnalités Principales

  • Gestion des Tables: Plan de salle visuel avec suivi en temps réel
  • Commandes: Création, modification, suivi des statuts
  • Paiements: Simple ou multiples (Espèces, TPE, En compte)
  • Synchronisation: Bidirectionnelle avec backend Laravel
  • Multi-rôles: Serveurs, Admins, Livreurs
  • Mode Hors-ligne: Fonctionnement complet sans connexion
  • Livraison: Gestion des livreurs et assignation
  • Comptabilité: Rapports détaillés par serveur et méthode de paiement

🛡️ Résolution de Conflits

Le système utilise plusieurs stratégies pour éviter les doublons et conflits:

🔍 Dédoublonnage des Commandes

Stratégie de matching (dans l'ordre):

  1. source_local_id - ID local stocké dans la commande distante
  2. table + total + heure - Pour commandes POS (tolérance 30s)
  3. téléphone + total - Pour commandes avec client identifié
  4. created_at + total + channel - Pour commandes API/Web

📊 Préservation du Statut Local

Quand une commande est tirée du backend, le statut local est comparé au statut distant. Si le statut local est plus avancé, il est conservé.

Ordre des statuts: pending → confirmed → preparing → ready → delivered

5. Conflits Identifiés

L'analyse détaillée de tous les fichiers a révélé 11 conflits potentiels, classés par sévérité:

🔴 #1 - Format JSON Invalide dans paymentSplit CRITIQUE

Fichier: lib/controllers/pos_controller.dart (ligne ~2545)

Problème: La méthode markOrderAsPaid() crée un JSON invalide:

// ❌ INCORRECT - produit: [{method: cash, amount: 150.0}]
order.paymentSplit = '[{method: ${order.paymentMethod}, amount: ${order.totalPrice}}]';

Contraste avec markOrderAsPaidWithSplit() qui produit du JSON valide:

// ✅ CORRECT - produit: [{"payment_method":"cash","amount":150.0}]
order.paymentSplit = jsonEncode(paymentList);

Impact: Tout code appelant jsonDecode() sur un paymentSplit créé par un paiement simple échouera.

Systèmes affectés:

  • "Mes Paiements" - ne peut pas parser les détails
  • "Comptabilité Admin" - montants incorrects
  • "Dashboard Admin" - statistiques faussées
  • Ticket d'impression - détails manquants

🟠 #2 - paymentSplit Non Synchronisé ÉLEVÉ

Fichiers:

  • lib/services/sync_queue_service.dart (lignes ~516-519)
  • lib/services/api_order_pull_service.dart (ligne ~1109)

Problème:

  • PUSH: Le payload de sync inclut payment_method et payment_status, mais PAS paymentSplit
  • PULL: Aucun champ payment_split n'est lu depuis la réponse backend

Impact: Les détails de paiement split sont perdus lors de la synchronisation.

🟠 #3 - _copyPosOrder Ne Copie PAS paymentSplit ÉLEVÉ

Fichier: lib/controllers/pos_controller.dart (lignes ~323-348)

Problème: Quand une commande est éditée via _copyPosOrder(), le champ paymentSplit n'est pas copié.

Impact: Si une commande payée avec split est éditée, les détails de paiement sont perdus définitivement.

🔵 #4 - paymentStatus Auto-Défini à 'paid' sur Confirmation MOYEN

Fichier: lib/controllers/pos_controller.dart (ligne ~2205)

if (normalizedStatus == 'confirmed') {
    order.paymentStatus = 'paid';  // ❌ Marque automatiquement comme payé
}

Problème: Quand une commande API/Web passe à confirmed, elle est automatiquement marquée comme payée, même sans paiement réel.

Justification: Pour les commandes Web/API, la confirmation implique le paiement en ligne.

Risque: Si une commande POS locale passe par ce chemin, elle pourrait être incorrectement marquée comme payée.

🔵 #5 - API Pull Écrase paymentMethod Local MOYEN

Fichier: lib/services/api_order_pull_service.dart (ligne ~1109)

Problème: Lors du pull, paymentMethod est toujours pris depuis le backend, sans préserver la valeur locale.

Contraste: staffId et paymentStatus ont une logique de préservation, mais PAS paymentMethod.

Impact: Si le backend a une valeur différente ou null, elle écrase le paiement local.

🔵 #6 - loadOrderForEdit Ne Restaure PAS paymentSplit MOYEN

Fichier: lib/controllers/pos_controller.dart (ligne ~2674)

Problème: Lors du chargement pour édition, _paymentMethod est restauré mais pas paymentSplit.

Impact: Si l'utilisateur sauvegarde sans modifier le paiement, paymentSplit est perdu.

🔵 #7 - Admin Accounting Définir paymentMethod Sans paymentSplit MOYEN

Fichier: lib/views/admin_accounting_screen.dart (lignes ~1297-1299)

order.paymentMethod = normalizePaymentMethod(paymentMethod);
order.paymentStatus = 'paid';
order.status = 'paid';
// ❌ paymentSplit n'est pas défini

Impact: Les commandes payées par l'admin n'ont pas de détails split, donc getParsedPaymentDetails() doit fallback sur paymentMethod.

⚫ #8 - paymentSplit Défini Avant markOrderAsPaid FAIBLE

Fichier: lib/views/pos_tables_screen.dart (lignes ~1395-1408)

Problème: La vue définit paymentSplit AVANT d'appeler markOrderAsPaid().

Statut: ✅ Actuellement sûr - markOrderAsPaid() vérifie si vide avant d'écrire.

Risque: Pattern fragile - dépend du fait que l'appelant définisse toujours paymentSplit en premier.

⚫ #9 - Multiples Endroits Modifient paymentStatus (Sans Mutex) FAIBLE

Fichiers: 6 fichiers différents

  • pos_controller.dart: markOrderPaid(), updateOrderStatus(), markOrderAsPaid(), markOrderAsPaidWithSplit()
  • pos_tables_screen.dart: dialog paiement
  • admin_accounting_screen.dart: paiement admin

Risque: Si deux opérations de paiement se produisent simultanément, la dernière écriture gagne.

⚫ #10 - updatePosOrder Écrit l'Objet Entier FAIBLE

Fichier: lib/services/database_service.dart (lignes ~441-449)

Problème: Utilise Isar.put() qui remplace le document entier.

Impact: Tout champ non défini sur l'objet au moment de l'update écrase la valeur précédente.

⚫ #11 - Sync Queue Dedup Ne Protège Pas les Écritures DB Concurrentes FAIBLE

Fichier: lib/services/sync_queue_service.dart (lignes ~414-426)

Problème: La déduplication empêche les entrées multiples dans la file, mais pas les écritures DB multiples avant le flush.

Impact: Dernière écriture gagne si updatePosOrder est appelé plusieurs fois rapidement.

9. Workflows Principaux

👨‍🍳 Workflow Serveur

Cycle de Vie Complet d'un Serveur

  1. Login → "Ouvrir le POS" sur écran login
  2. POS Lock → Entrer PIN 4-6 chiffres ou scanner badge
  3. POS Menu → 5 cartes d'action:
    • Nouvelle Commande → Choix type (Sur place/À emporter/Livraison)
    • Mes Commandes → Liste filtrable avec actions
    • Mes Paiements → Totaux du jour par méthode
    • Mes Tables → Plan de salle visuel
    • Mobile/Web → Commandes API/Web/Pickup
  4. Prise de Commande:
    • Sélection table ou type (pickup/delivery)
    • Ajout articles depuis catalogue
    • Sauvegarde → status: pending
  5. Paiement:
    • Depuis "Mes Commandes" ou "Table" → Bouton "Payer"
    • Choix: Simple (1 méthode) ou Split (multiple)
    • Confirmation → paymentStatus: paid
    • Si table occupée → libération table
  6. Verrouillage → Bouton "Verrouiller" → Retour POS Lock

👔 Workflow Admin

Cycle de Gestion Admin

  1. Login → Email/Mot de passe sur écran login
  2. Dashboard Admin → Vue d'ensemble:
    • Stats: Tables, Web/Mobile, CA, Total CMD
    • Répartition paiements: TPE, Cash, En compte
    • 9 tuiles d'accès rapide
  3. Comptabilité (/admin-accounting):
    • Sélecteur de date
    • Revenu par canal (POS vs Web/API)
    • Revenu par type (Sur place, Emporter, Livraison)
    • Répartition par méthode de paiement
    • Résumé par serveur avec nombre de commandes
  4. Gestion Commandes (/admin-orders):
    • Filtres: statut, canal, serveur
    • Changement de statut
    • Annulation avec motif (admin seul)
    • Vue détaillée avec articles
  5. Gestion Utilisateurs → CRUD complet
  6. Import Data → Sync manuelle depuis API distante

🔄 Workflow de Synchronisation

Sync Automatique en Arrière-plan

Timer toutes les 60 secondes:

  1. Étape 1: PUSH
    • Scanner commandes non sync (queueUnsyncedOrders())
    • Scanner utilisateurs non sync (queueUnsyncedUsers())
    • Envoyer file au backend (flushQueue())
  2. Étape 2: PULL
    • Récupérer utilisateurs depuis backend
    • Récupérer commandes API entrantes
  3. Étape 3: UI Refresh
    • Si nouvelles commandes → loadOrdersToday()
    • Si commandes API en attente → Son de notification

Événements immédiats:

  • Création commande → Enqueue + flush après 700ms
  • Modification commande → Enqueue seul
  • Changement statut API → HTTP direct (non queue)

🔑 Authentification API

Token-Based (Laravel Sanctum)

  • Obtention: Via /api/login ou /api/login-pin
  • Stockage: AuthSessionService local
  • Propagation: Automatique à tous les services sync
  • Refresh: Via PIN ou credentials si expiré
  • Endpoints publics: /api/sync/public/ ne requiert pas Authorization

⚡ Gestion d'Erreurs

Code HTTP Signification Traitement
422 Validation failed Essai statuts alternatifs: pending → confirmed → delivered
403 Non autorisé Après 3 essais → dead-letter queue
429 Rate limited Exponential backoff: 5s → 10s → 20s → ... → 5m max
5xx Server error Retry 3 fois → dead-letter queue
Offline Pas de réseau Item reste dans file, retry au prochain flush
